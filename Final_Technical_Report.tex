\section{Project Scenario \& Background}
% ==========================================
Our university campus hosts multiple student societies, including the Gaming Society, Sports Society, Developers Club, Literary Society, and Media Society. These organizations are responsible for executing events, workshops, competitions, recruitment drives, and awareness campaigns throughout the academic semester.

\subsection{Current Challenges}
The absence of a centralized digital platform for managing student societies creates significant communication gaps, inefficient event handling, poor record management, and a lack of administrative oversight. Currently, society operations are handled manually through fragmented channels such as WhatsApp groups, disjointed spreadsheets, paper-based registrations, and verbal communication. 

\subsection{Problem Statement}
Manual systems waste time, increase errors, and reduce student engagement. Students often miss important announcements, event registrations become disorganized, duplicate memberships occur, and attendance records are often inaccurate. Society leaders also face difficulty coordinating members, assigning logistical tasks, collecting feedback, and maintaining historical records. Furthermore, the university administration lacks visibility into society performance, active memberships, event approvals, and resource allocation. There is no centralized system to monitor or regulate society activities effectively.

\subsection{Proposed Solution}
To solve these issues, we have developed a desktop-based \textbf{Societies Management System} built using C\# Windows Forms and Microsoft SQL Server. This platform digitally connects students, society representatives, and university administration, automating society registrations, event management, announcements, task coordination, approvals, and reporting.

\section{Functional Requirements}
% ==========================================
The system satisfies the following exhaustive list of requirements across three primary user roles.

\subsection{1. Student Functional Requirements}
\begin{enumerate}
    \item Students shall be able to create accounts and log in securely.
    \item Students shall be able to browse available societies.
    \item Students shall be able to apply for membership in societies.
    \item Students shall be able to join multiple societies.
    \item Students shall be able to view upcoming society events.
    \item Students shall be able to register for events online.
    \item Students shall be able to view their membership status.
    \item Students shall be able to view event tickets/passes.
\end{enumerate}

\subsection{2. Society Functional Requirements}
\begin{enumerate}
    \item Society heads shall be able to create and manage society profiles.
    \item Society heads shall be able to approve or reject membership requests.
    \item Society members shall be able to manage internal member lists.
    \item Societies shall be able to create, update, and cancel events.
    \item Societies shall be able to assign tasks to members.
    \item Societies shall be able to generate reports of members and events.
\end{enumerate}

\subsection{3. Admin Functional Requirements}
\begin{enumerate}
    \item Admin shall be able to manage all student accounts.
    \item Admin shall be able to create, approve, suspend, or delete societies.
    \item Admin shall be able to monitor all society activities.
    \item Admin shall be able to approve event requests.
    \item Admin shall be able to generate university-wide reports.
\end{enumerate}

\section{Task 1: System Implementation \& Database Architecture}
% ==========================================
The application is implemented as a robust .NET desktop application built on an N-Tier architectural pattern. This design ensures high maintainability, scalability, and separation of concerns by isolating data access, business logic, and presentation layers.

\subsection{Architectural Project Structure}
The \texttt{FASTSocietiesSystem} solution is organized into the following logical layers:

\begin{itemize}
    \item \textbf{UI (User Interface)}: Contains the Windows Forms implementation. It utilizes a programmatic design approach to implement the \textit{Midnight Editorial} aesthetic. The \texttt{UI/Forms} directory contains 29 distinct forms for various user roles, while \texttt{UI/Helpers} manages the custom \texttt{ThemeManager} and modern UI components.
    \item \textbf{BLL (Business Logic Layer)}: Acts as the brain of the system. It contains services like \texttt{SocietyService}, \texttt{StudentService}, and \texttt{AuthenticationService} that enforce university policies, validate user actions, and coordinate between the UI and the data layer.
    \item \textbf{DAL (Data Access Layer)}: Implements the Repository Pattern using ADO.NET to interact with SQL Server. Each entity has a dedicated repository class (e.g., \texttt{EventRepository}) to manage CRUD operations and complex queries, ensuring the database logic is decoupled from the business logic.
    \item \textbf{Models}: Contains the core domain entities such as \texttt{User}, \texttt{Society}, \texttt{Event}, and \texttt{Task}. These are POCO (Plain Old CLR Objects) classes used to transport data across all layers of the application.
\end{itemize}

\subsection{Database Architecture \& Schema}
The system utilizes a highly normalized Microsoft SQL Server database. The schema is designed to maintain data integrity and support complex relationships required for society management.

\begin{itemize}
    \item \textbf{Core Entities}: The database tracks Users (with role-based access), Societies (with status tracking), and Events.
    \item \textbf{Relational Mapping}: Explicit junction tables manage memberships (connecting Students to Societies) and registrations (connecting Students to Events).
    \item \textbf{Audit Logging}: A centralized \texttt{SystemLog} table tracks all critical administrative actions and society activities for monitoring purposes.
\end{itemize}

The complete database schema is documented in \texttt{database-schema-clean.sql}, and the structural relationships are visualized in the \texttt{docs/erd.puml} artifact.

\subsection{Detailed Database Entity Analysis}
The relational schema is comprised of 9 core tables designed to handle the complex state management of the university ecosystem:

\begin{itemize}
    \item \textbf{Users}: The central identity table. Stores \texttt{UserId}, \texttt{Email}, \texttt{PasswordHash}, \texttt{FullName}, and \texttt{Role} (Student, SocietyHead, Admin). The \texttt{Status} column manages account activity (Active, Suspended).
    \item \textbf{Societies}: Tracks organizations. Linked to \textbf{Users} via \texttt{HeadId} (1:1 relationship for management). Includes \texttt{Status} for administrative approval cycles.
    \item \textbf{Memberships}: A junction table between \textbf{Users} and \textbf{Societies} (M:N). Tracks student enrollment, \texttt{JoinDate}, and \texttt{MembershipStatus} (Pending, Approved).
    \item \textbf{Events}: Contains logistical data for society activities. Linked to \textbf{Societies} via \texttt{SocietyId} (1:N). Includes \texttt{Capacity}, \texttt{EventDate}, and \texttt{Location}.
    \item \textbf{EventRegistrations}: A junction table between \textbf{Users} and \textbf{Events} (M:N). Manages student attendance, registration deadlines, and \texttt{AttendanceStatus} (CheckedIn, Absent).
    \item \textbf{Tasks}: Internal management entity. Linked to \textbf{Societies} and optionally assigned to a specific \textbf{User}. Includes \texttt{Priority} and \texttt{DueDate}.
    \item \textbf{Announcements}: Broadcast system for societies. Linked to \textbf{Societies} and the creating \textbf{User}.
    \item \textbf{SystemLogs}: Audit trail table. Stores a global record of all administrative actions, society creations, and critical security events linked to a \texttt{UserId}.
    \item \textbf{ApprovalRequests}: Workflow management table. Centralizes all pending approvals for new Societies and Events, linking requesters to administrative targets.
\end{itemize}

\subsection{Entity Relationship Diagram (ERD)}
The following diagram illustrates the relational structure of the FAST Societies Management System. It captures the complex interactions between users, their hierarchical roles, and the operational entities managed within the system.

\begin{figure}[H]
    \centering
    \includegraphics[width=0.95\textwidth]{../ERD.png}
    \caption{Entity Relationship Diagram (ERD) of the FAST Societies System}
    \label{fig:erd}
\end{figure}

The ERD establishes several critical relationships:
\begin{itemize}
    \item \textbf{One-to-Many (Users to Societies)}: A single Administrator or Society Head can manage multiple society records, while each society is tied to a primary head for accountability.
    \item \textbf{Many-to-Many (Students to Societies)}: Captured via the \texttt{Memberships} junction table, allowing students to belong to multiple societies while societies maintain a roster of numerous members.
    \item \textbf{One-to-Many (Societies to Events/Tasks)}: Societies act as the parent container for all operational activities. Deleting a society triggers a cascade that manages associated event and task lifecycles.
    \item \textbf{Hierarchical Role Linking}: The \texttt{Users} table is self-referencing or linked via roles to ensure that permissions (Admin vs Student) are strictly enforced across all database queries.
\end{itemize}

\subsection{Key Relational Constraints}
\begin{itemize}
    \item \textbf{Referential Integrity}: All foreign keys are constrained with \texttt{ON DELETE NO ACTION} or \texttt{CASCADE} where appropriate to prevent orphaned records (e.g., deleting a society removes its associated tasks).
    \item \textbf{Data Consistency}: Unique constraints are applied to emails in the \texttt{Users} table and registration pairs in \texttt{EventRegistrations} to prevent duplicate entries.
\end{itemize}

\section{Task 6: KLM Usability Evaluation}

The Keystroke-Level Model (KLM) is a predictive modeling technique used to estimate the time it takes an expert user to complete a task on a given user interface. By decomposing tasks into fundamental physical and cognitive operators, we can objectively evaluate the efficiency of the FAST Societies Management System.

\subsection{KLM Operators \& Methodology}
The evaluation utilizes the following standard execution times for each operator:
\begin{itemize}
    \item \textbf{K} (Keystroke) = 280 ms: Pressing a key or a mouse button.
    \item \textbf{M} (Mental preparation) = 1350 ms: The time required for the user to cognitively prepare for the next physical action.
    \item \textbf{P} (Pointing) = 1100 ms: Moving the mouse to a target on the screen.
    \item \textbf{H} (Homing) = 400 ms: Moving the hand between the keyboard and the mouse.

\end{itemize}

In conclusion, the UI architecture provides a high-throughput environment suitable for university-scale administration, where speed of processing (e.g., approving hundreds of event requests) is a critical requirement.

\section{Task 7: COCOMO Cost Estimation}
% ==========================================
The \textbf{Constructive Cost Model (COCOMO)} is a procedural software cost estimation model that uses a mathematical formula to predict the effort and duration required for a project based on the size of the software (measured in KLOC).

\subsection{Model Selection \& Justification}
COCOMO defines three distinct modes based on the project's environment and complexity:
\begin{itemize}
    \item \textbf{Organic Mode}: Small, stable teams with flexible requirements and a familiar environment.
    \item \textbf{Semi-Detached Mode}: Intermediate teams with a mix of experienced and inexperienced staff and moderately rigid requirements.
    \item \textbf{Embedded Mode}: Large teams with tight constraints, complex hardware interfaces, and rigid regulations.
\end{itemize}

The \textbf{Organic Mode} was selected for the FAST Societies Management System. This is justified by the project being a university-level development within a stable ecosystem (.NET), using a small team of developers who are highly familiar with the requirements and technology stack.

\subsection{Basic COCOMO Mathematical Framework}
The model utilizes four primary coefficients ($a, b, c, d$) that vary by mode. For the Organic mode, these are:
\begin{itemize}
    \item \textbf{$a = 2.4$ (Effort Scale Factor)}: Determines the base effort required per unit of size.
    \item \textbf{$b = 1.05$ (Effort Complexity Factor)}: Accounts for the slight non-linear increase in effort as size grows.
    \item \textbf{$c = 2.5$ (Schedule Scale Factor)}: Determines the base time required relative to the effort.
    \item \textbf{$d = 0.38$ (Schedule Complexity Factor)}: Accounts for the non-linear relationship between effort and duration.
\end{itemize}

\end{enumerate}
